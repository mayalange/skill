# Матрица QA: типовой API и workflow

Применяйте только подходящие разделы. Сначала прочитайте OpenAPI/контракт, SDD-задачу и диаграмму состояний; если правило или ожидаемый HTTP-статус не определены, зафиксируйте это как вопрос/риск, а не как дефект.

## Создание сущности

- Проверьте обязательные, необязательные, `null`, пустые, неизвестные и лишние поля; формат, границы и межполевые ограничения.
- Проверьте корректный статус, тело ответа, идентификатор, начальное состояние, автора/tenant и серверные поля. Клиент не должен подменять серверные поля.
- Проверьте дубли: уникальные ключи, повторную отправку, idempotency key и отсутствие дублированных событий/побочных эффектов.
- Проверьте атомарность: при ошибке сохранения, события или внешнего вызова не остаётся частично созданная сущность.
- Проверьте права: пользователь может создавать только разрешённый тип/сущность и только в своей области доступа.

## Получение сущности

- Проверьте идентификаторы: существующий, отсутствующий, некорректный и принадлежащий другому tenant/пользователю.
- Сверьте тело ответа с контрактом: обязательность полей, типы, enum, даты/таймзоны, decimal/деньги, маскирование чувствительных данных.
- Проверьте, что после создания и разрешённого перехода возвращаются актуальное состояние, версия и доступные действия, если они предусмотрены контрактом.
- Проверьте согласованное поведение `404`/`403` в соответствии с политикой раскрытия существования ресурса.

## Поиск по критериям

- Проверьте каждый фильтр отдельно, комбинацию фильтров (обычно логическое AND), пустой результат, `null`/пустое значение, границы диапазонов и некорректные значения.
- Проверьте изоляцию tenant и прав доступа: поиск не раскрывает чужие сущности ни в `items`, ни в `total`/агрегациях.
- Проверьте пагинацию: первая/последняя/пустая страница, предельный размер, неверный номер, стабильная сортировка и отсутствие пропусков/дублей между страницами.
- Проверьте сортировку: разрешённые поля, направление, `null`, детерминированный вторичный ключ и запрет неразрешённых полей.
- Проверьте, что фильтрация выполняется в хранилище и не создаёт N+1 или неограниченную выборку на изменённом пути.

## Workflow, action и guard

Составьте таблицу: `текущее состояние × action × роль/условие -> следующее состояние | отказ`.

- Для каждого разрешённого перехода проверьте целевое состояние, ответ API, аудит/событие и требуемые побочные эффекты.
- Для каждого запрещённого перехода проверьте код/формат ошибки и отсутствие изменений в БД, событиях и внешних системах.
- Проверьте guard: он выполняется до изменения состояния, использует актуальные данные и возвращает понятную причину отказа без утечки закрытых данных.
- Проверьте права отдельно от guard: отсутствие роли не должно обходиться подходящими параметрами, а подходящая роль не должна обходить бизнес-условие.
- Проверьте повтор action, конкурентные action и устаревшую версию сущности. Не допускайте двойных переходов, дублированных событий и потери данных.
- Проверьте terminal-состояния, отмену/rollback, переходы назад и недостижимые состояния, если они предусмотрены.
- Если API отдаёт список доступных `actions`, сравните его с реальным выполнением: действие показано тогда и только тогда, когда роль и guard позволяют его выполнить.

## Общие контрактные проверки

- Сверьте HTTP-метод, путь, коды ответов, заголовки, JSON-схему, форматы ошибок и обратную совместимость с опубликованным контрактом.
- Проверьте отсутствие лишних полей в ответе и неприём неоговорённых полей в запросе, если контракт требует строгую схему.
- Проверьте трассировку/audit: кто, когда и каким action изменил сущность; не включайте персональные или секретные данные в логи.

## Минимальный набор сценариев для каждого изменённого endpoint

1. Успешный сценарий.
2. Валидационная ошибка.
3. Ошибка авторизации или прав доступа.
4. Граничное или дублирующее условие.
5. Побочный эффект или его отсутствие при ошибке.
6. Сценарий, непосредственно выведенный из требования/SDD-задачи.
